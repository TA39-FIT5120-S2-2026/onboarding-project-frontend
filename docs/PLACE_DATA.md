# Place data

`src/data/cbdPlaces.js` is the static list behind every location picker in
the app (origin/destination on Route Planner, and the location field on
Refuges and Forecast). This documents where it comes from and how to
regenerate it.

## Why a static list, not a geocoder

`API_CONTRACT.md` takes coordinates, not addresses, and there is no
geocoding endpoint. The obvious fix - calling a third-party geocoder like
Nominatim - was deliberately rejected: it would send whatever the user types
off-device on every keystroke, which is the wrong trade for an app built
around "no login, no accounts, nothing stored" for a vulnerable user group.
A curated, pre-verified list keeps everything on-device.

## Where the list comes from

Three sources, combined in `CBD_PLACES`:

1. **`src/data/cbdPlaces.generated.js`** - real City of Melbourne landmarks
   (name + coordinates) from the backend's seeded `landmarks` table,
   filtered to walkable-destination themes and **verified one at a time
   against the backend's actual `POST /api/routes/validate` polygon check**.
   Generated by `scripts/generate-cbd-places.mjs`. Never hand-edited.
2. **`COLLOQUIAL_PLACES`** (`scripts/placeOverrides.js`) - names the
   landmarks dataset doesn't have under a recognisable label but people will
   type anyway (Bourke Street Mall, Chinatown). Verified the same way.
3. **`OUTSIDE_COVERAGE_PLACES`** (`scripts/placeOverrides.js`) - real places
   the backend's polygon rejects, kept selectable so AC 1.1.1 Scenario 3
   (destination outside the CBD) stays reachable from the combobox instead
   of only from free text. The combobox marks these "outside our coverage
   area" before submit.

## Coverage is narrower than "the CBD"

The backend validates against the CLUE **"Melbourne (CBD)"** small area, a
specific ABS/City-of-Melbourne statistical boundary - not colloquial "the
CBD". This is a real, verified fact, not a bug:

- Re-tested Southern Cross Station, Flagstaff Gardens, Docklands Library and
  Princes Bridge against their real landmark coordinates (not approximate
  ones) - all four still fall outside the polygon.
- Flagstaff *Railway Station* is inside; Flagstaff *Gardens*, 200m away, is
  not.

If the backend's CBD boundary is ever redefined, rerun the generation script
- some `OUTSIDE_COVERAGE_PLACES` entries may then pass and should move into
the generated list.

## Regenerating the list

1. Export CBD-area landmarks from the backend's database:
   ```sql
   SELECT id, theme, sub_theme, feature_name, latitude, longitude
   FROM landmarks
   WHERE latitude BETWEEN -37.8230 AND -37.8050
     AND longitude BETWEEN 144.9480 AND 144.9780;
   ```
   Convert the tab-separated result to a JSON array of
   `{id, theme, sub_theme, feature_name, latitude, longitude}` objects.

2. With the backend running (`npm run dev` in `onboarding-project-backend`,
   database seeded):
   ```
   node scripts/generate-cbd-places.mjs --landmarks path/to/landmarks.json
   ```
   This overwrites `src/data/cbdPlaces.generated.js`. Run
   `npm test -- src/data/__tests__/cbdPlaces.test.js` afterwards.

3. To adjust which landmark themes are offered, or add/remove a colloquial
   or out-of-coverage entry, edit `scripts/placeOverrides.js` and rerun.

## Known limitation

The landmarks dataset yields far fewer walkable destinations than a real
geocoder would (44 generated + 2 colloquial + 9 out-of-coverage, at time of
writing) - see `docs/BACKEND_GAPS.md` for the same limitation as it affects
the Sensory Refuges feature.
